# KeyGap：预期优势、实现要求与验证路径

## 研究目标

先明确 agent 设计应当产生的优势，再把设计实现到确实具备这些优势，最后用针对性实验验证；任何新增模块首先应当相对 naive 近似无损。

## 核心设计一：Storyboard

**期望优势：** 把简短、泛化的用户故事扩充为更丰富的可见情节，并根据真实播放时长分配更合理的事件节奏。

**无损要求：** Storyboard 只提供清晰的故事与时间指导，不应让后续绘画任务显著变复杂、降低角色绘制能力或破坏运动质量。

**当前状态：** 60 帧 naive 消融中，storyboard-conditioned 版本的情节明显更丰富，绘画能力未观察到明显下降；当前先保留设计。

**后续实验：** 对多类简短 prompt 比较 ordinary naive 与 storyboard-conditioned naive，盲评情节丰富度、节奏、事件完成率和视觉质量。

## 核心设计二：时间线拆分为 Gaps

**期望优势：** 在中长任务中避免后段角色崩坏、3D 结构过度简化和细节减少，并提高超长序列的完整生成率与局部细节量。

**无损要求：** 对 naive 能稳定完成的短中任务，拆分本身不应降低逐帧绘画、身份一致性、运动连续性或故事完成质量。

### Gap 输入契约

Gap 与 naive 使用完全相同的 system drawing prompt；gap 的局部事件描述等价于 naive 的 `User request`，唯一新增的视觉输入是相邻的 `FROM` 和 `TO` keyframes。

正常 gap 输入只包含：

1. 当前 gap 的局部事件描述与目标退出状态；
2. 维度、局部帧数、每帧时长和需要生成的中间帧编号；
3. `FROM` 与 `TO` 两张已接受的边界 keyframe。

正常 gap 不再接收完整 storyboard、原始总任务、frame 1 identity reference、previous/next keys、全局 ID 白名单或额外的 segment 指令。

### Key 输入契约

Keys、gaps 与 naive 使用完全相同的 system drawing prompt；完整 storyboard 等价于 keys 的 `User request`，唯一新增的任务信息是完整播放时长和需要输出的稀疏 key indices。

Keys 使用与 naive 相同的 `{"frames": [...]}` 输出 schema，不再要求额外返回 `static_ids`，也不再通过后处理强制固定全局静态 strokes。

### 验证顺序

1. **无损检查：** 在 24–80 帧任务上，用相同局部描述比较 one-shot naive 与 KeyGap，确认绘画和运动质量没有系统性下降。
2. **长度优势：** 在 128、192 和更长任务上比较完整生成率、后段角色形态、身份漂移和事件完成率。
3. **细节优势：** 在长 3D 任务上比较物体真实空间结构、线框结构复杂度和后段结构保持情况。
4. **故事优势：** 在欠描述任务上比较情节丰富度、因果完整性和节奏。
5. **工程优势：** 比较并行 wall time、失败后的局部重试成本，以及修改单个事件时需要重画的帧数和 token。

## 当前重点观察指标

- 3D 长任务是否把物体和场景结构画得过于简单；
- 靠后帧是否出现腿部异常拉长、头部变扁等角色形态崩坏；
- 行走和跑动是否保持腿部交替、支撑相和 passing pose；
- gap 边界是否出现停顿、速度突变、姿势跳变或身份变化；
- 长任务后段的每帧细节是否明显少于前段。
